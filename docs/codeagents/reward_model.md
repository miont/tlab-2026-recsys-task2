# Reward model и награда в RL

> Как устроена и обучается reward model (этап 3) и что считается наградой на этапе 4. Код: `src/recsys_rl/reward_model.py`, `src/recsys_rl/rewards.py`. Цифры качества — `docs/codeagents/observations.md`, §2.

Если коротко: reward model (RM) — это обученный симулятор реакции пользователя. По истории прослушиваний и треку-кандидату она предсказывает, как пользователь отреагирует на этот трек. Основная награда в RL — предсказанная доля прослушивания трека (`played_ratio`).

## 1. Зачем нужна RM

Логи офлайновые: известна реакция только на треки, которые пользователь реально слушал. Во время RL политика предлагает любой из примерно 200k треков, и для почти всех таких пар «контекст → трек» реального фидбэка нет. Поэтому реакцию на них предсказывает модель.

## 2. Устройство (`reward_model.py`)

Схема называется late fusion: история и кандидат кодируются отдельно и соединяются только в конце.

- **Энкодер истории.** Это такой же GPT-2, как базовая модель, и он получает те же входы: трек плюс фидбэк каждого прошлого прослушивания (бин ratio, лайки). Его скрытое состояние `h_{t-1}` описывает историю до момента t.
- **Представление кандидата `c`.** Это эмбеддинг трека плюс признаки, известные в момент рекомендации:
  - бин длины трека;
  - `is_organic` (в RL он равен 0, то есть трек пришёл из рекомендации);
  - сколько раз трек уже встречался в контексте. Повторы — самый сильный сигнал в EDA.
- **Головы.** Несколько MLP получают на вход `[h, c, h·c]` и выдают 6 предсказаний:

| Голова | Что предсказывает |
|---|---|
| `ratio` | долю прослушивания трека, от 0 до 1 |
| `listen_plus` | вероятность, что доля ≥ 0.5 |
| `skip` | вероятность, что доля < 0.3 |
| `like` / `dislike` | вероятность лайка или дизлайка на этом прослушивании |
| `continue` | вероятность, что сессия продолжится (следующее прослушивание в пределах 30 минут) |

- **Ансамбль.** Голов `rm.n_ensemble = 4`, энкодер у них общий. Разброс их предсказаний служит оценкой неуверенности модели (epistemic uncertainty). Он показывает, где RM экстраполирует, например на треках, которые пользователь никогда не слушал.

Почему именно late fusion: один проход трансформера оценивает сразу G кандидатов одного контекста. В RL это нужно постоянно, потому что на каждый контекст сэмплируется 16 треков. То же нужно для переранжирования top-100 и анализа всего каталога. Минус такой схемы в том, что кандидат не может напрямую «смотреть» на историю.

## 3. Обучение

1. **Данные.** Только train-окна и только реальные прослушивания. Используется teacher forcing: за один проход для каждого прослушивания t окна предсказывается его фидбэк по состоянию `h_{t-1}`. Своего фидбэка и всего, что было позже, модель не видит.
2. **Метки.** Это реальная реакция на прослушивание t. Учитывается только то, что наблюдалось до границы периода: лайк, поставленный после конца train, не считается train-меткой. `continue` неизвестен, если `t + gap` выходит за границу (`feedback_targets`).
3. **Лосс.** Для `ratio` это soft BCE, для остальных голов — обычная BCE, без весов классов. Отсутствие весов оставляет вероятности откалиброванными, а это важно, потому что они напрямую идут в награду. Ожидаемая калибровочная ошибка (ECE) по `ratio` на val получилась около 0.006.
4. **Бутстрэп.** Каждый член ансамбля получает свой вес окна из распределения Poisson(1). Так головы обучаются на немного разных выборках, и их разброс несёт смысл.
5. **Валидация.** Качество проверяется на val-дне (`FeedbackSet`), ранняя остановка — по val loss.

## 4. Proxy и gold

Обучаются две RM (`notebooks/03_reward_model.ipynb`):

- **`rm_proxy`** даёт награду в RL. Её энкодер инициализирован из `base`, обучена на всех пользователях.
- **`rm_gold`** нужна только для оценки, политика её никогда не оптимизирует. Чтобы её ошибки меньше совпадали с ошибками proxy, она отличается: случайная инициализация, другой seed, 80% пользователей, аудиоэмбеддинги.

Такая пара позволяет поймать «взлом» награды (reward hacking). Если proxy-награда растёт, а gold — нет, политика эксплуатирует ошибки proxy, а не улучшает рекомендации. Этот риск реален: на этапе 3 у proxy нашлось смещение к популярным и уже прослушанным трекам, которого почти нет у gold (`observations.md`, §2.2).

## 5. Что считается наградой (`rewards.py`)

RL здесь сформулирован как одношаговый контекстный бандит: контекст — история пользователя, действие — один трек, награда — функция от предсказаний proxy RM (среднее по ансамблю) для этого трека. Вариант выбирается через `rl.reward`.

| Вариант | Награда | Смысл |
|---|---|---|
| **R1 `ratio`** (основная) | E[played ratio] | дослушает ли пользователь трек |
| R2 `listen_time` | ratio × длина трека (не больше `rl.listen_time_cap` = 600 с), в минутах | время прослушивания |
| R3 `like_ratio` | p(like) + ratio/10 | явный позитивный фидбэк |
| R4 `debiased_ratio` | ratio − средний train-ratio для бина длины | убирает выгоду коротких треков |
| R4 `item_debiased_ratio` | ratio − средний train-ratio трека (со сглаживанием к общему среднему) | убирает выгоду треков, которые «всегда дослушивают» |
| R6 `continue` | p(сессия продолжится) | удержание |

К любому варианту можно добавить штрафы R5:
- `rl.repeat_penalty` за трек, который уже есть в контексте;
- `rl.dislike_penalty` × p(dislike);
- `rl.uncertainty_penalty` × разброс ансамбля. Он штрафует треки, где RM не уверена и с большей вероятностью ошибается.

Статистики длины и среднего ratio считаются только по train.

Почему основная награда — `ratio`: это самый плотный и надёжный сигнал. Доля прослушивания есть у каждого события, а лайков всего около 0.7%, дизлайков около 0.08%. Голова `ratio` к тому же лучшая по качеству, Spearman 0.66 против 0.46 у бейзлайна. Головы `dislike` и `continue` почти не лучше среднего по пользователю, поэтому награды на них (R5-dislike и R6) заведомо шумные.

## 6. Главное ограничение

RM обучена только на треках, которые пользователи реально слушали, а политика предлагает и такие, которых пользователь никогда не видел. На них RM экстраполирует. Поэтому в RL нужны три страховки:
- KL-штраф к π_ref (базовой модели), чтобы политика не уходила далеко от неё;
- контроль по gold RM;
- при необходимости штраф за неуверенность (`rl.uncertainty_penalty`).
